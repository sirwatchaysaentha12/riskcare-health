# Data Program / Coding & UI Review Guidelines

## วัตถุประสงค์
ใช้เป็นแหล่งข้อมูลหลักสำหรับตรวจสอบการเขียนโค้ดและการตกแต่งเว็บไซต์ในทุกด้าน โดยยึดตามข้อกำหนดของโปรเจกต์และต้องไม่กระทบฟังก์ชันการทำงานเดิม

## 1. มาตรฐานการเขียนโค้ด

### 1.1 โครงสร้างโค้ด
- หลีกเลี่ยงการเขียนโค้ดรวมกันเป็นไฟล์เดียวขนาดใหญ่ (Monolithic)
- แยกส่วน UI, หน้า, คอมโพเนนต์, สไตล์, ฟังก์ชันช่วย และข้อมูลให้ชัดเจน
- ใช้โครงสร้างแบบ Component-Based ตามหน้าที่ดังนี้
  - components: คอมโพเนนต์ย่อยที่นำกลับมาใช้ซ้ำได้
  - pages: หน้าหลักของระบบ
  - styles: ไฟล์สไตล์ตามหน้า/ฟีเจอร์
  - assets: รูปภาพและสื่อ
  - utils/hooks/services: ฟังก์ชันช่วยและการเชื่อมข้อมูล

### 1.2 การตั้งชื่อไฟล์และตัวแปร
- ตั้งชื่อไฟล์ให้สื่อความหมายตรงกับหน้าหรือฟังก์ชัน
- ใช้ชื่อตัวแปรและฟังก์ชันที่อ่านง่ายและสอดคล้องกันทั้งโปรเจกต์
- เลี่ยงการตั้งชื่อสั้นเกินไปหรือคลุมเครือ

### 1.3 ความสะอาดของโค้ด
- ไม่มี Import ที่ไม่ถูกใช้
- ไม่มีโค้ดที่ไม่ถูกเรียกใช้งาน (Dead Code)
- ลบโค้ดซ้ำหรือปรับให้สั้นลงโดยไม่กระทบการทำงาน
- จัดเรียง Import, State, Logic และ JSX แบบเป็นระเบียบ

## 2. มาตรฐาน UI/UX และการตกแต่งเว็บไซต์

### 2.1 สีหลักของระบบ
- ปุ่มและแถบเมนูหลักต้องใช้สี #0E4B95
- พื้นหลังหน้าเว็บหลักต้องใช้ #F7F9FC
- พื้นหลังกล่องประเมินฝั่งซ้ายใช้ #E6F0FA
- ตัวอักษรทั่วไปใช้ #555555

### 2.2 การ์ดระดับความเสี่ยง
- ระดับ 1 (แดง): ขอบและข้อความ #D32F2F / พื้นหลัง #FFEBEE
- ระดับ 2 (ส้ม): ขอบและข้อความ #E65100 / พื้นหลัง #FFF3E0
- ระดับ 3 (เหลือง): ขอบและข้อความ #FBC02D / พื้นหลัง #FFFDE7
- ระดับ 4 (เขียว): ขอบและข้อความ #388E3C / พื้นหลัง #E8F5E9

### 2.3 หลักการออกแบบหน้าเว็บ
- ใช้สไตล์เรียบง่าย ทันสมัย และเป็นมืออาชีพ
- คงความสอดคล้องของสีและ spacing ทั่วทั้งระบบ
- ใช้ border-radius ที่นุ่มนวลและ shadow ที่พอดีเพื่อความน่าเชื่อถือ
- ให้ข้อความอ่านง่ายและไม่รก

## 3. ความถูกต้องของฟีเจอร์แบบประเมินความเสี่ยง

### 3.1 แบบสอบถาม
- แสดงคำถาม 14 ข้อตามหมวด
  - ข้อมูลพื้นฐาน
  - ประวัติสุขภาพ
  - พฤติกรรมและสิ่งแวดล้อม
  - อาการปัจจุบัน
  - ความปลอดภัย
- บังคับให้ตอบครบทุกข้อก่อนดูผล
- แสดงจำนวนข้อที่ตอบแล้ว

### 3.2 การคำนวณผลลัพธ์
- คำนวณระดับความเสี่ยงตาม prototype scoring ที่กำหนดใน data.md
- Red flag ต้องเปลี่ยนผลเป็นคำเตือนเร่งด่วนทันที โดยไม่รอคะแนน
- คำแนะนำต้องไม่อ้างว่าเป็นการวินิจฉัยโรค

### 3.3 การแสดงผลและ Modal
- หลังกดประเมินให้แสดงสถานะกำลังประมวลผลก่อนแสดงผลจริง
- ปุ่มประเมินต้องถูกปิดการกดระหว่างประมวลผล
- ผลลัพธ์ต้องแสดงในหน้าเดียวหรือผ่าน Modal อย่างสอดคล้อง

## 4. ความถูกต้องของระบบเปลี่ยนหน้า
- ใช้ react-router-dom สำหรับการเปลี่ยนหน้า
- Login ต้องสามารถพาไปยัง Dashboard ได้ทันทีเมื่อเข้าสู่ระบบ
- Dashboard ปุ่ม “เริ่มประเมิน” ต้องไปที่ /assessment
- หน้า Assessment ต้องมีปุ่มกลับไป /dashboard

## 5. QA / Testing Checklist

### 5.1 UI/UX
- ตรวจความเรียบร้อยของ layout ทั้ง Desktop และ Mobile
- ตรวจ spacing, border radius, และความชัดเจนของข้อความ
- ตรวจว่าองค์ประกอบไม่ล้นจอและไม่แยกกันเกินไป

### 5.2 Form Validation
- ตรวจว่าปุ่มประเมินถูก disable จนกว่าจะตอบครบทุกข้อ
- ตรวจข้อความแจ้งเตือนเมื่อข้อมูลไม่ครบ
- ตรวจว่าการสลับคำตอบและการส่งข้อมูลเป็นไปอย่างต่อเนื่อง

### 5.3 Edge Cases
- ตรวจการกด Back/Forward ของเบราว์เซอร์
- ตรวจการโหลดช้าและการตัดการเชื่อมต่อเครือข่าย
- ตรวจการกรอกข้อมูลไม่สมบูรณ์หรือข้อมูลผิดพลาด

## 6. ข้อควรระวังเมื่อปรับปรุงระบบ
- ห้ามเปลี่ยนหน้าตาและฟังก์ชันหลักโดยไม่ได้รับอนุมัติ
- ห้ามลบ Logic ที่จำเป็นของระบบ
- หากมีส่วนที่เสี่ยงต่อการทำให้ระบบผิดพลาด ควรระบุไว้เป็นข้อเสนอแนะแทนการแก้ไขทันที

## 7. คำสรุปสำหรับทีมพัฒนา
- ให้โค้ดอ่านง่ายและดูแลรักษาได้
- ให้ UI/UX สอดคล้องและปลอดภัยสำหรับผู้ใช้
- ให้การเปลี่ยนหน้าและฟังก์ชันแบบประเมินทำงานถูกต้องเสมอ
- ตรวจสอบทั้งโครงสร้างโค้ดและคุณภาพของหน้าเว็บอย่างต่อเนื่อง
